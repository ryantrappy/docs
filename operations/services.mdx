Use this workflow to inspect, change, and recover services on Trappserver. Start with the [inventory](/services/overview) to identify the owning deployment and persistent data.

## Inspect before changing

```sh
docker ps
docker ps -a
docker stats --no-stream
docker logs --tail 100 paperless-webserver-1
docker inspect paperless-webserver-1 --format '{{json .State.Status}}'
docker inspect paperless-webserver-1 --format '{{json .Mounts}}'
```

Replace the example container with the service you are investigating. Read logs locally; redact credentials or personal data before copying them into documentation.

Check the app's supporting database or broker too. Container health alone does not validate DNS, Caddy routing, or login.

## Inspect native and off-host services

Plex, CrashPlan, UPS management, disk monitoring, and SSH run directly on Ubuntu. Public dynamic DNS uses the Komodo `cloudflare-ddns` stack; native `ddclient` is stopped and disabled. Use [Native host services](/services/host) to identify their systemd units:

```sh
systemctl status plexmediaserver.service crashplan.service --no-pager
journalctl -u plexmediaserver.service -n 100 --no-pager
systemctl status pwrstatd.service smartmontools.service --no-pager
systemctl status ssh.socket ssh.service --no-pager
findmnt /media/internal/fourteenTB
curl -I http://192.168.1.236:32400/web/
```

Check mounted media disks before troubleshooting missing Plex files. CrashPlan's unit can report `MainPID=0` while its engine runs; see [Backups, power, and storage](/infrastructure/host-reliability) for the process check and the unverified backup coverage.

Home Assistant and UniFi run off-host. Use [Homelab devices](/infrastructure/devices) to locate their endpoints and reported topology. A successful HTTP response or online client does not validate automations, backups, or all network functions.

## Update a service

1. Record the current image and app release, deployment source, and data paths.
2. Confirm the backup includes both application files and database state where required.
3. Read the upstream release notes for the installed version and target version.
4. Apply the update through the existing manager.
5. Check the updated container, its dependencies, logs, and browser response.
6. Record the result in the service page.

Many services use moving tags such as `latest`, `release`, or `:2`. Those tags do not identify the exact release currently running. Local images such as Caddy and rankings need their existing build workflow.

Watchtower is stopped with restart disabled. Komodo owns application updates; TeslaMate PostgreSQL, Network Optimizer's InfluxDB, and Paperless PostgreSQL are excluded from their stacks' global automatic updates.

## Separate DNS, proxy, and application failures

From the LAN:

```sh
dig @192.168.1.1 radarr.ryantr.app A +short
curl -I https://radarr.ryantr.app
curl -I --resolve radarr.ryantr.app:443:192.168.1.236 https://radarr.ryantr.app
```

Radarr has a local record in the migration notes. The normal and `--resolve` checks compare DNS routing with direct access to Caddy.

If the direct Caddy check fails, review [Caddy setup](/infrastructure/caddy), the upstream container, and its host port. If the direct check succeeds but the normal hostname fails, investigate DNS or the client's route.

A Caddy LAN guard only governs traffic that passes through Caddy. Direct host ports have their own reachability controls.

## Backup and recovery planning

The mounts in each service reference identify storage that exists. They do not establish a working backup policy. Use the [backup coverage register](/operations/backup-coverage) for recovery inputs, artifact evidence and gaps. The 2026-10-02 coverage work ran no backups or restore tests.

| Service area | Recovery data to identify |
| --- | --- |
| Komodo | MongoDB volumes, keys, Core configuration, deployment definitions, and backups |
| Caddy | Caddyfile, custom build definition, certificate data, and deployment credentials |
| Immich | Database backup, uploads, external-library files, and matching mount paths |
| Paperless | Documents, app data, database/export, and AI companion state |
| Media | App configuration and selected media/download files |
| Native Plex | Plex data directory, coordinated database backup, and separately protected media files; see [Plex](/services/plex) |
| Host services | CrashPlan selections and restore test, UPS configuration, mount definitions, and operational configuration; see [Backups, power, and storage](/infrastructure/host-reliability) |
| Off-host services | Home Assistant backups and restore method, UniFi configuration backup, and coordinator settings; coverage not inspected |
| Rankings | MongoDB data, source revision, local build, and required application state |
| Tandoor | Recipe media and the still-unverified database location |
| TeslaMate | PostgreSQL data, dashboards, MQTT configuration, and logger deployment |
| Other tools | The bind mounts and named volumes listed in their reference pages |

Use application-supported database backups or a coordinated shutdown/snapshot strategy. A raw copy of an active database directory is not a verified recovery procedure. Follow the app's documentation for its installed release.

Retain volume names and host paths when restoring. Removing a container does not automatically restore its deployment configuration or data.

## Complete a change

Before marking any homelab change complete, add a dated entry to the [Changelog](/changelog). This applies to deployments, configuration, services, networking, storage, security and documentation.

1. Update the affected service reference and checklist status.
2. Add or extend the current UTC date in the changelog. State the actual change, affected services, verification results and any deferred work or required user action.
3. Save the documentation changes with the same change delivery. Create or update the GitHub PR and leave merging to the owner; Codex must never attempt a PR merge or request broader permissions to merge. Report the PR link and that publication awaits the owner's merge.
4. Keep credential values and private recovery material out of the entry.

Do not describe a proposal, unverified deployment or pending publication as completed. Record reversions and corrections as new outcomes so the history remains useful.

## Privileged management access

Docker control is host-administrator access. Periphery is the only retained socket-mounted container. Komodo and Homelable MCP require authentication and direct management ports are limited to LAN/server-local clients by the persistent host policy.

Use the separate `homelab-inventory` login for read-only Server/Stack/Repo access through Komodo or MCP local OAuth login. Use an administrator identity only for intended deployments. The protected local inventory credentials are at `/home/trappserver/codex_docs/management-access-20261002/inventory-access.json`. Homelable MCP keys grant application tool access and have no configured per-key read-only scope. Never publish credentials or add the deployment super-admin token to an inventory client.
