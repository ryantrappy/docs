## Skylight and iCloud Reminders grocery sync

The user service `skylight-reminders-sync.service` on `trappserv.er` supports the Home Assistant automation **Sync Skylight and Trap House Grocery Lists**. Home Assistant emits `skylight_reminders_sync_requested` on list changes, item additions/completions, startup and a one-minute fallback. The worker serializes requests and also checks list contents every 30 seconds, catching changes that leave the incomplete-item count unchanged.

The worker stores separate Skylight and iCloud UIDs with per-field baselines and durable write intents. Additions reconcile in both directions; completion, reactivation and renaming update the paired UID. Entity polling timestamps never determine ownership. Pending writes prevent stale responses from reversing changes, and unknown additions are not blindly repeated. Ambiguous unlinked names and concurrent edits require review. Historical completed duplicates remain untouched; absence does not automatically delete or recreate a paired item.

Configuration, Python source, pinned `websockets==15.0.1` virtual environment, owner-only credential and `links.json` live under `/home/trappserver/codex_docs/skylight-reminders-sync/`. The unit is at `~/.config/systemd/user/skylight-reminders-sync.service`; user lingering was already enabled. The credential expires on 2027-10-08 and must be renewed before then. Preserve `links.json` in private backups: it contains item titles and the persistent ID pairings. This task did not establish off-host backup coverage.

Check `sensor.skylight_reminders_sync` in Home Assistant for `ok`, `attention` or `paused`, linked-item count, pending writes and warnings. The service must stay running on the homelab host; provider polling still determines when external edits become visible. For rollback, stop/disable the worker first, then restore `automation.before.json` through the HA configuration API and enable the original automation. Restoring automation code does not undo list changes. Keep recovery data private; never run both implementations simultaneously.

## Dynamic DNS

**Updated — 2026-10-02:** Cloudflare DDNS is the sole updater for public server A records. The Komodo `cloudflare-ddns` stack manages all thirteen current records; each matched the current WAN IPv4 address at verification.

The legacy `ddclient.service` used `protocol=dyndns2` with `domains.google.com` and was reporting failed updates. It is now stopped and disabled in systemd and legacy SysV startup. The installed package and configuration are retained for rollback; do not restart it alongside Cloudflare DDNS.

The private pre-disable configuration backup is `/home/trappserver/codex_docs/komodo-migration/ddclient-config-before-disable-20261002`. ## Terminal access and authentication monitoring

TCP 22 was listening on IPv4 and IPv6. The SSH service was running with a disabled unit-file state, while ssh.socket was active and enabled. Socket activation explains why SSH is available with the service itself disabled.

The OpenSSH package is **1:9.6p1-3ubuntu13.19**. On **2026-09-30**, the effective server configuration was evaluated for `trappserver` and `ai-agent` using a temporary test host key. Ordinary users have password and public-key authentication enabled, keyboard-interactive authentication disabled, and root password login prohibited (`PermitRootLogin prohibit-password`, reported as `without-password`). The local drop-in requires a public key and disables password authentication and forwarding for `ai-agent` only. The live daemon was not reconfigured during this check.

Fail2Ban **1.0.2-3ubuntu0.1** is running. Its resolved on-disk configuration includes the SSH jail with a 10-minute ban interval, 10-minute observation interval, and five retries. The live jail and ban state could not be read without root access. See [host listeners and network separation](/todo/security-and-consistency#16-review-host-listeners-and-network-separation) for the remaining policy review.
