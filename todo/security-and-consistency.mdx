This checklist began with a **read-only review on 2026-09-29**, supplemented by infrastructure references checked on 2026-09-28. The initial review made no changes. Completed items and migration notes below record subsequent work. Work through one item at a time.

**Scope:** Docker runtime settings, selected readable deployment files, credential file permissions, host listeners, database versions, and existing homelab documentation. Router rules, internet reachability, effective application passwords, backup restores, and a full vulnerability scan were not tested. A port bound to every interface is a confirmed configuration finding; it does not by itself prove internet exposure.

Keep secret values, recovery codes, and private keys out of this page. Recheck each finding before changing a service.

## Suggested order

| Priority | Start with |
| --- | --- |
| P1 — first | Credentials, management access, unsupported databases, and usable backups |
| P2 — next | Update ownership, container privileges, proxy security, logging, and recovery behavior |
| P3 — cleanup | Port mismatches, stale routes, library paths, and duplicate automation |

Before a change, identify the owning deployment, record the current version/configuration, and confirm a rollback or restore method. Use [Service operations](/operations/services) for the workflow. Changes to generated files under `/etc/komodo` may be overwritten; fix the owning Komodo settings or source repository.

## P1 — credentials and access

### 01. Protect and replace exposed deployment credentials

**Evidence — confirmed:** The rankings checkout's `.git/config` contains a credential in its HTTPS remote URL and has mode `0644`. The checkout directories were readable by the current non-root account. Homelable's `.env` has mode `0664` and includes `MCP_API_KEY`, `SECRET_KEY`, and a password-hash setting. Other inspected credential stores, including `~/.git-credentials` and `~/.codex/config.toml`, already use `0600`.

**Suggested fix:** Restrict access to the affected files and checkout directories through the owning deployment workflow. Replace the affected Git credential, use the narrowest repository permissions needed, and avoid persisting reusable credentials in readable remote URLs where the manager supports another mechanism. Review Homelable key exposure and rotation requirements, including effects on existing sessions and MCP clients. Check whether old credentials also appear in private logs, backups, or Git history; document locations without copying values here.

- [ ] **Done when:** Only intended accounts can read credential-bearing files, replaced credentials are revoked, deployments still authenticate, and the next Komodo refresh does not recreate the exposure.

### 02. Restrict direct management and application ports

- [x] **Complete — 2026-09-29:** Implemented the requested scope: remote direct access to applications marked `internal-only` in Caddy is restricted to **192.168.1.0/24**. Host loopback and server-local Docker bridge integrations remain trusted. Other TODO items were not remediated.

**Protected direct TCP ports:**

| Application | Host ports |
| --- | --- |
| Watcharr | 3080 |
| Radarr | 7878 |
| SABnzbd | 8282 |
| Sonarr | 8112 |
| Homebridge | 8581 |
| Komodo | 9120 |
| Portainer, including agent/tunnel access | 8000, 9000, 9443 |
| Scrutiny | 8081 |
| Maintainerr | 6246 |
| UniFi gateway | 80, 443 on 192.168.1.1 |

**Host implementation:** Root-owned `/usr/local/sbin/homelab-internal-ports` installs IPv4 and IPv6 rules in dedicated chains. `INPUT` protects native/host-network listeners and Docker's `DOCKER-USER` protects forwarded published ports. Conntrack matches the original host port after Docker DNAT, so mappings such as SAB's host `8282` to container `8080` are covered. Direct routing from non-LAN sources to private Docker container addresses is also restricted. Docker's own rules are preserved; UFW was not enabled or changed. See [Docker's recommended firewall integration](https://docs.docker.com/engine/network/firewall-iptables/).

**Persistence:** `homelab-internal-ports.service` is enabled and active. `/etc/systemd/system/docker.service.d/lan-port-access.conf` requires the policy to run before Docker. No production container restart was needed. Remote IPv6 access to the protected direct ports is blocked because Caddy currently defines only an IPv4 LAN. Update both policies before introducing an IPv6 LAN.

**Gateway implementation:** UniFi policy `6abbdea53f39a091c770be88`, **LAN-only UniFi management: block VPN**, blocks VPN → Gateway TCP `80,443`, always on, for both address families. LAN access is preserved; existing External, Hotspot, and DMZ default gateway blocks remain. The firewall snapshot comparison confirmed exactly one new policy with no changes to existing policies, zones, or groups. Readback places the new rule at index `10000`, before the predefined allow at `2147483647`. The separate ordering API returned 401; no reordering was performed.

**Verification:** Temporary network namespace probes showed all eleven host ports blocked from non-LAN IPv4 and IPv6 sources. A simulated LAN source reached all ten running ports. Packet counters confirmed both the native INPUT and IPv4 Docker DNAT forwarding paths were exercised. Public HTTPS returned 200 on both address families, and active internal Caddy routes remained available. Test containers, links, and routes were removed.

**Limitations:** Scrutiny already has no listening upstream: direct port `8081` refuses LAN connections and its Caddy route returns 502. This remains for item 18. Boot dependency ordering was checked, but a production reboot was not performed. Gateway verification used configuration readback; an actual VPN/WAN client test was not available. Services outside Caddy's `internal-only` set, including the separate MCP listeners, were outside this requested change.

**Maintenance and rollback:** Implementation, verification results, and before/after snapshots are under `/home/trappserver/Documents/caddy_v2/internal-port-access/`; use its `README.md`. Reload the host policy with `sudo systemctl reload homelab-internal-ports.service`. The script's `remove` command removes only its own rules; disable boot installation and remove the Docker drop-in when rolling back permanently. Roll back UniFi by disabling or removing only the named policy. Avoid restoring an old full firewall snapshot over current Docker rules.

### 03. Treat Docker management and MCP tools as privileged access

**Evidence — confirmed mounts and listeners; authorization needs verification:** Portainer, Komodo Periphery, and Watchtower mount the Docker socket. The Komodo MCP server publishes host port `8003`; Homelable MCP publishes `8001`. Socket access can permit control of the host through Docker. MCP authentication and effective tool permissions were not tested. See [Docker daemon security](https://docs.docker.com/engine/security/).

**Suggested fix:** Keep management tools on a trusted network/VPN and verify authentication, account permissions, and token scopes. Give MCP integrations only the access they need and separate read-only inventory use from deployment or destructive actions where supported. Keep socket mounts only on components that require them; a read-only bind flag alone is not a Docker API authorization policy.

- [ ] **Done when:** Unauthenticated requests are rejected, each integration has documented permissions, and Docker control is available only to trusted administrators and required services.

## P1 — databases and recovery

### 05. Migrate TeslaMate away from PostgreSQL 13

**Evidence — confirmed runtime:** `teslamate_database_1` reports PostgreSQL **13.23**. PostgreSQL 13 support ended on **2025-11-13**, so this major version no longer receives community fixes. See the [PostgreSQL versioning policy](https://www.postgresql.org/support/versioning/).

**Suggested fix:** Identify the TeslaMate release and its supported database versions. Take an application-consistent backup, prove a restore in isolation, and plan a supported major-version migration. Changing the image tag while reusing an old database directory is not a migration.

- [ ] **Done when:** TeslaMate uses a supported PostgreSQL major version, historical data and dashboards work, and a tested backup plus rollback plan exist.

Immich server remained at version **3.2.4**.

**Migration:** Stopped Immich writes, made a checked custom-format PostgreSQL 14 dump, initialized a separate PostgreSQL 18 data directory, and restored the dump in a single transaction before cutover. ### 09. Complete the Blocky transition and reduce its privileges

**Evidence — confirmed:** Blocky still runs with `privileged=true`, a writable configuration mount, DNS on all interfaces, and a published HTTP port. ### 10. Verify certificates on internal upstream connections

**Evidence — confirmed configuration/documentation:** Caddy's Portainer TLS route uses `tls_insecure_skip_verify`. The UniFi upstream has no explicit HTTPS transport. The documented UniFi DNS automation disables controller certificate verification.

**Suggested fix:** Use a certificate and hostname that clients can verify, or trust a suitable private CA in the relevant client. Configure upstream TLS intentionally. Coordinate trust changes with the DNS sync and other integrations so they continue working. Browser-facing Caddy HTTPS does not secure every upstream hop. See [Caddy transport options](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy#the-http-transport).

- [ ] **Done when:** Proxy and automation connections verify the intended server identity, no skip-verification exception remains unexplained, and DNS automation still succeeds.

### 11. Review public app authentication and ingress paths

**Evidence — confirmed proxy classification; effective protection needs verification:** Home Assistant, Ombi, rankings, Invoice Ninja, Tandoor, Paperless, and Immich routes lack Caddy's LAN-only guard. Cloudflared also runs. Router forwards, tunnel destinations, application authentication, and MFA coverage were not audited.

**Suggested fix:** Confirm which apps intentionally accept internet traffic. Verify application authentication and MFA where supported, review tunnel/router destinations, and keep administrative endpoints private. For browser-only private apps, consider an identity-aware access layer; account for mobile clients, webhooks, and APIs before adding one. Test Caddy's peer-address guard against each actual ingress path instead of assuming forwarded headers or a tunnel preserve the expected source address.

- [ ] **Done when:** Every public route has an intentional audience and tested authentication, private routes remain blocked over each ingress path, and legitimate integrations still work.

### 12. Narrow writable mounts and container permissions

**Evidence — confirmed mounts:** Ombi and Overseerr mount the entire `/media` tree writable. Duplicate Finder also has broad writable media access. Caddy mounts static site content writable even though it serves files. Several containers explicitly add broad capability lists.

**Suggested fix:** Review what each application actually writes. Remove unnecessary mounts, narrow them to required directories, and use read-only access for consumers. Preserve write access for tools intentionally editing or deleting media. Reduce capabilities and use a non-root application user where the image supports it; test permissions per service rather than applying a blanket change.

- [ ] **Done when:** Each writable path and capability has a documented purpose, browsing-only apps cannot modify media/site content, and intended workflows still succeed.

### 13. Add bounded Docker log retention

**Evidence — confirmed:** Most running containers use `json-file` with empty rotation options. The inspected daemon configuration has no logging defaults. Network Optimizer's speed-test container already sets `max-size=10m` and `max-file=3`. Docker's default JSON log size is unlimited. See [Docker JSON logging](https://docs.docker.com/engine/logging/drivers/json-file/).

**Suggested fix:** Define a retention budget and use rotation settings consistently, either in deployment definitions or daemon defaults. Preserve enough logs for diagnosis. Existing containers need recreation to inherit new daemon defaults; plan that through each owning manager.

- [ ] **Done when:** Active containers have bounded logs, required diagnostic history remains available, and disk-usage alerts are tested.

A health check alone does not automatically restart an unhealthy container.

**Suggested fix:** Verify the backend listener, then change the source configuration to `http://backend:8000` if it is the intended endpoint. Review allowed browser origins separately; do not broaden CORS to hide the problem.

- [ ] **Done when:** MCP can read the backend through service DNS, browser access works from approved origins, and no dependency on the host port remains.

Map each DNS updater to its provider and record names, and remove overlap only after establishing which updater should own each record.
